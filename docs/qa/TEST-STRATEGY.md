# Test strategy: how the STP is executed and evidenced

This document explains how each level of the Software Test Plan (STP) is performed in the repository, how it is automated, and where the evidence ends up. The STP says *what* must be verified; this says *how* and *with which tool*.

## 1. Levels, tools and where they run

| STP level / type | Tool (as named in the STP) | Location | What it proves |
| --- | --- | --- | --- |
| Unit | PyTest, Vitest | `backend/tests/<story>/`, `frontend/src/**/*.test.js` | Business rules: rubric normalisation, state machine, 48 h freeze boundary, GPA maths, validators |
| Integration (module + DB) | PyTest against MySQL | `backend/tests/<story>/` | REST endpoints, ORM mapping, auth middleware and real SQL together; includes negative paths and concurrency |
| Integration (black-box API) | **Newman** | `qa/newman/` (collection generated by `build_collection.py`) | The deployed HTTP surface end to end: cookies, forced password reset, full grade lifecycle incl. the once-only dispute, session revocation, RBAC matrix, injection inertness |
| System / E2E | **Playwright** | `qa/e2e/tests/` | Real browser flows across roles; TC-UX-01 (≤ 3 clicks), responsive layouts at 375/768/1920 px, theme, focus handling |
| Accessibility | Playwright + **axe-core** | `qa/e2e/tests/03-accessibility.spec.js` | Automated WCAG 2.1 A/AA rules on every role's screens and dialogs |
| Performance | **k6** (container) | `qa/k6/load.js` | 500 concurrent sessions, p95 < 800 ms (SYS-NF-001); 200 simultaneous submissions without failure or deadlock (SYS-NF-002) |
| Security (dynamic) | **OWASP ZAP** (container) | `qa/zap/`, `qa/openapi/` | Spec-driven authenticated active scan of all 55 API operations, plus passive baselines of the API and the nginx-served UI, all through nginx |
| Security (static) | Bandit, pip-audit, npm audit | `qa/run.py static` | Python code smells, vulnerable dependencies |
| Security (functional) | PyTest + Newman | `backend/tests/admin_metrics/test_security.py`, Newman folders 01, 13, 14 | TLS 1.3 only, HSTS/Secure cookie, HTTP-only 48 h JWT, expiry/tamper, RBAC on every endpoint, SQLi/XSS |
| Acceptance (UAT) | Manual, with automated pre-checks | `docs/uat/` | See section 4 |

## 2. One command, locally and in CI: everything runs in Docker

The host needs only Docker (Compose v2). The application itself is containerised (`docker-compose.yml`: MySQL, Flask under gunicorn, nginx serving the React build), and the QA tooling runs in a second, isolated stack (`docker-compose.qa.yml`, project `srs-qa`) with its own in-memory database, re-seeded before every black-box stage. It never touches your development stack or a local MySQL.

```powershell
./qa.ps1 consistency   # OpenAPI spec current, acceptance criteria covered, frontend builds   (./qa.sh on macOS / Linux / CI)
./qa.ps1 unit          # PyTest (MySQL) + Vitest, coverage gate >= 70 %
./qa.ps1 static        # Bandit, pip-audit, npm audit
./qa.ps1 integration   # Newman against the API container
./qa.ps1 perf          # k6 container
./qa.ps1 zap           # OWASP ZAP container, scanning through nginx
./qa.ps1 e2e           # Playwright against the nginx-served UI
./qa.ps1 uat           # executable UAT script: fills docs/uat/UAT-RESULTS.md, screenshots in docs/uat/evidence/
./qa.ps1 docs          # regenerate openapi.json, acceptance matrix, UAT script
./qa.ps1 demo          # re-record the sprint demo videos
./qa.ps1 all           # consistency..e2e, then the report
```

| Container | Image | Role |
| --- | --- | --- |
| `db` | `mysql:8.0` | Database (`--max-connections=600`: four API workers each hold a pool) |
| `api` | `backend/Dockerfile` | gunicorn, 12 worker processes x 2 threads (the QA stack uses this production sizing; the laptop dev stack uses 4 x 4) |
| `web` | `frontend/Dockerfile` | nginx: static React build, `/api` reverse proxy, the security headers |
| `qa` | `qa/Dockerfile` | PyTest, Vitest, Newman, Playwright + Chromium, Bandit, pip-audit, ffmpeg |
| `k6` | `grafana/k6` | Load test |
| `zap` | `ghcr.io/zaproxy/zaproxy` | Dynamic security scan |

### GitHub Actions (`.github/workflows/ci.yml`)

Runs on every pull request to `main`, on every merge to `main`, nightly, and on demand. Each job is just `bash qa.sh <stage>` plus an artifact upload, so the pipeline and a laptop run the same thing. Documentation-only changes skip it (they have their own PDF workflows).

| Job | Command | Blocks the merge? |
| --- | --- | --- |
| `consistency` | `qa.sh consistency` | yes |
| `unit` | `qa.sh unit` | yes |
| `integration` | `qa.sh integration` | yes |
| `static-security` | `qa.sh static` | yes |
| `dast` | `qa.sh zap` | yes |
| `e2e` | `qa.sh e2e` | yes |
| `performance` | `qa.sh perf` | yes |
| `report` | assembles `TEST-EXECUTION-REPORT.md` from every job's artifacts | evidence only |

To make "yes" mean something, enable branch protection on `main` (Settings, Branches) and mark those jobs as required status checks. The nightly run exists because dependency vulnerabilities are published against code that has not changed.

## 3. Pass/fail gates

A build is green only if all of these hold (they are computed by `qa/report.py` and also enforced by the individual tools):

* every executed STP test case passes (TC → evidence mapping in `qa/traceability/tc_map.py`);
* backend line coverage ≥ 70 % (SYS-NF-005, TC-QUAL-01);
* k6: p95 < 800 ms with 500 sessions and < 1 % failed requests; the 200-request burst has zero failures (the thresholds also require a minimum request count, so an empty run cannot pass vacuously);
* ZAP reports no High/Critical alert (STP exit criterion); Bandit has no medium+ finding; no known-vulnerable production dependency;
* every acceptance criterion in `stories.md` is mapped to at least one automated check and every reference still exists.

## 4. Acceptance testing

Customer acceptance is manual by nature, so the aim is to make it fast, complete and traceable:

1. `docs/uat/UAT-PLAN.md`: who, when, entry/exit criteria, severity scale.
2. `docs/uat/UAT-SCRIPT.md`: generated per story from `stories.md` and the smoke-test steps (click-by-click, with the expected result).
3. `docs/uat/UAT-RESULTS.md`: the single sheet the customer fills in (PASS / FAIL / BLOCKED per criterion, defect numbers, exploratory-session findings, sign-off table).
4. `docs/uat/ACCEPTANCE-MATRIX.md`: for each of the 51 criteria, the automated tests that already prove it, so the customer's manual run confirms rather than discovers.
5. The sprint demo videos in `demo/videos/` act as pre-UAT evidence of the working product.

Regenerate the derived documents with `./qa.ps1 docs` (it never overwrites a filled-in `UAT-RESULTS.md`).

## 5. Reports and evidence (STP section 8 deliverables)

| STP deliverable | Produced by |
| --- | --- |
| Automated test scripts | `backend/tests`, `qa/newman`, `qa/e2e`, `qa/k6`, `qa/zap` |
| Test data seed scripts | `backend/app/seed`, `python manage.py seed --reset` |
| Test execution logs and coverage reports | `qa/reports/<stage>/` (JUnit XML, HTML coverage, k6 JSON, ZAP HTML/JSON, Playwright HTML); CI uploads them as artifacts for 30 days |
| Defect reports and triage | GitHub issues (labels `defect`, `uat`); security findings in `SECURITY-TRIAGE.md` |
| Final Test Execution & Acceptance Report | `qa/reports/TEST-EXECUTION-REPORT.md`, built from the result files, containing the STP section 14 metrics (executed %, passed %, requirement coverage) |

## 6. Known limits (what these tests do *not* establish)

* **TC-OPS-01 (99 % monthly availability)** can only be measured in production over a month. It is recorded as *waived*: the course instructor agreed that scenarios which only make sense in a real organisation are written into the STP and, where not feasible to test, may be closed without execution. The test report lists it separately from the executed cases. The evidence the project can offer is the health endpoint plus the nightly CI run.
* **Load tests run the app, database and k6 on one machine**, with four server processes. They show the architecture meets the latency target with ample headroom; they are not a capacity forecast for 10,000 users.
* **ZAP scans the system as a client sees it**: through the nginx container, which owns the security headers (CSP, framing, nosniff, ...). It cannot see TLS: HSTS and TLS 1.3 belong to whatever terminates HTTPS in production and must be configured and scanned there.
* **axe-core finds roughly a third of accessibility problems.** Keyboard-only and screen-reader checks are part of the manual exploratory charters.
* **TLS 1.3** is verified by a handshake test against the application's own TLS context; in production TLS terminates at the reverse proxy, which must be configured and scanned separately.
